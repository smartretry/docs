This page covers what you need to get right in your own integration. For certifications, data residency, retention, and contractual commitments, see the [SmartRetry security page](https://www.smartretry.com/security).
 
## Card data
 
SmartRetry does not store card numbers. Card numbers and CVV are not retained once a transaction reaches a final status, and where card data appears in logs or storage it is masked.
 
For repeat billing you can send a stored payment token instead of raw card details, which removes the need to re-transmit card data on every charge. See [Payment methods](/docs/integration/payment-methods) for how tokenized payments work.
 
<Note>
  Because SmartRetry transmits cardholder data on your behalf, your own PCI DSS obligations still apply to how you collect and send that data. Using tokenized flows reduces the scope you have to cover.
</Note>
## Transport
 
All connections are encrypted with TLS. TLS 1.3 is negotiated by default and TLS 1.2 is the enforced minimum — TLS 1.0 and 1.1 are rejected at the edge.
 
Do not disable certificate verification in your HTTP client, including in staging.
 
## Access control
 
Dashboard access uses role-based access control. A **User Master** manages the client account and creates additional users; a **User** has day-to-day operational access. Additional roles can be configured on request.
 
Multi-factor authentication is required at login for every user.
 
API keys are separate from dashboard accounts and authenticate server-to-server requests only. See [Authentication](/docs/authentication) for how to handle them safely.
 
<Warning>
  If you believe your API key has been exposed, contact [security@smartretry.com](mailto:security@smartretry.com) immediately so it can be revoked and replaced.
</Warning>
## Webhooks
 
Your webhook endpoint is a public URL. Verify the signature on every incoming payload before acting on it, and reject anything that fails. See [Webhooks](/docs/integration/webhooks) for the signature scheme and verification examples.
